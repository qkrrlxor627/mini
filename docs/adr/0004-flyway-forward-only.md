# ADR-0004: Flyway 단방향 마이그레이션 정책

## Status
Accepted

(날짜: 2026-05-08)

## Context
학습 중 스키마가 꼬였을 때 어떻게 회복할지 결정 필요.

후보:
- **A**: `docker compose down -v`로 볼륨 삭제 → 빈 DB로 시작 → V1부터 다시 적용
- **B**: 꼬인 V1을 그대로 수정해서 다시 적용 (체크섬 무시 옵션으로 우회)
- **C**: V1은 절대 수정하지 않고 V_n으로 정공 복구 ✅

관련 Step: 2~3 (마이그레이션 작성).

배경:
- 운영 DB는 `down -v` 같은 카드 못 씀 — 프로덕션 데이터 날리면 끝.
- Flyway는 적용된 마이그레이션의 **체크섬을 저장** → V1을 사후 수정하면 다른 환경에서 마이그레이션 거부됨.
- 본 프로젝트는 학습용이지만 **운영 시뮬레이션**이 학습 가치의 핵심.

## Decision
**Flyway 단방향 정책.** V1 절대 수정 금지. 변경은 V2부터 추가만. 학습 중 스키마 꼬여도 `docker compose down -v`로 회복하지 않고, 새로운 V_n 마이그레이션으로 정공법 복구.

## Rationale

**A (down -v)를 안 고른 이유:**
- 운영 환경에서 절대 못 하는 행동 → 학습 효과 0.
- "어차피 학습이니까"라며 의존하면 운영 감각이 안 생김.
- 마이그레이션 history가 매번 리셋 → 진짜 어려운 시나리오(데이터가 이미 들어간 상태에서 스키마 변경)를 한 번도 안 겪게 됨.

**B (V1 수정 + 체크섬 우회)를 안 고른 이유:**
- Flyway 체크섬 검증 회피는 **운영에서 절대 금기**. 한 번 통과시키면 팀이 그 우회에 의존하게 됨.
- 다른 환경(개발자 PC, CI, 운영)이 모두 어긋남 — "내 PC에선 되는데" 사고 출처.
- 마이그레이션 history의 진실성 자체가 깨짐.

**C (단방향 + V_n 복구)가 주는 학습 가치:**
- 운영 DB와 동일한 제약 아래서 회복 시뮬레이션.
- "스키마 변경 = 새 마이그레이션 추가"라는 멘탈 모델 정착.
- 누적되는 V_n이 시간에 따른 결정의 흔적을 보존 — 코드 고고학 가능.

## Consequences

**좋은 면:**
- 운영 감각 — 실제 회사 환경에서 그대로 쓰는 룰.
- 마이그레이션 히스토리 보존 — V1, V2를 보면 도메인 진화 흐름이 보임 (예: V1은 `balance NUMERIC`, V2는 `balance_amount`/`balance_currency`로 분할).
- 다른 환경(CI, 협업자) 간 일관성 보장.

**나쁜 면:**
- 학습 초반 짜증 — "한 줄만 고치면 되는데" 싶을 때 새 V_n 작성해야 함.
- V_n 누적으로 마이그레이션 파일 수 증가 (실무에선 일정 시점에 V1로 squash하는 옵션 있음).
- 잘못 짠 V_n을 되돌리려면 또 V_n+1 필요 — 사고 시 복잡도 ↑.

**재검토 신호:**
- 학습 초기 단계(Step 1~3)는 본 룰을 엄격히. Step 5 이후엔 자연스러워질 것.
- 진짜 꼬여서 회복 못 할 정도면 — `down -v`가 아니라 **`flyway repair`** 명령 학습 기회로 삼는다.
- 협업 인원이 늘면 V_n squash 정책을 별도 ADR로 추가 검토.
